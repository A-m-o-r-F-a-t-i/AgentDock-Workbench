# AgentDock Workbench Release 文案规则

　　Release 说明是面向用户的版本变更说明。每次创建、更新或同版本重新发布 Release 时，都使用同一套规则。

## 1. 比较基线

　　每个版本都描述**目标版本相对上一个对外发布版本的完整差异**。例如 1.1.8 的比较基线是 1.1.7。

　　同一版本因为修复安装包、重新编译、替换资产或再次预发布时，比较基线不改变。Release 正文继续描述该版本相对上一版本的完整变化，不增加“本次重新预发布更新”“某日重发内容”“本次只合并了哪些 PR”等临时章节。

　　编写前先检查：

```text
上一发布标签..目标发布标签
```

　　同时按平台和功能阅读相关设计文档，不能只根据最后几条 PR、最后一次构建或当前会话中的修改写正文。

## 2. 内容组织

- 先写用户能够感知的主要变化，再写内部可靠性和安全边界。
- 大版本能力要给足篇幅。例如新增 Android 原生 Workbench、安装方式变化、跨平台客户端新增等，应单独成章并说明实际功能范围。
- 同类修复归入对应功能章节。重新上传前新增的 Windows、Android、macOS 或 Agent 修复，应合并到 Windows、Android、macOS 或工具章节，不单独列为“重新发布修复”。
- 安装速度、启动方式、回退策略、兼容性、权限语义等会改变用户体验的变化必须写明。
- PR 编号、内部工作线名称和临时任务名只用于开发记录，不能代替用户可理解的功能说明。

## 3. 不写入 Release 正文的内容

　　以下信息保留在 PR、Actions、审计或发布恢复记录中，不放进面向用户的 Release 正文：

- CI、单元测试、模拟器、安装测试或回归测试的通过/失败结果；
- Actions run ID、job 数量、覆盖率、测试样本数量和构建耗时；
- “本次重新发布”“本次重发”“重新预发布日期”等过程性记录；
- 仅描述最后一批 PR 的增量列表；
- 发布脚本调试、草稿 Release ID、标签迁移或资产替换过程。

　　Release 可以说明真实的产品限制，例如 Android 使用测试签名、某平台仍需要外部 Termux、某功能有版本或环境要求；这些属于用户安装和使用条件，不属于测试结果。

## 4. 下载区域

　　下载部分保持简洁，只说明平台与应选择的安装包。通常使用一张短表即可。

　　架构名存在明显误解风险时，可以增加一两句必要说明；不要把 Release 尾部写成完整安装教程。详细安装步骤放入项目文档。

## 5. 同版本替换

　　同版本替换 Release 时：

1. 保留该版本的完整 canonical Release 说明；
2. 将替换前新增的用户可见改动归并到原有平台/功能章节；
3. 不保留重发日期标题和“与上一批安装包相比”的临时段落；
4. GitHub Release 正文与仓库中的 `docs/releases/vX.Y.Z.md` 保持一致。

## 6. 交付检查

　　发布前至少人工检查以下文案条件：

- 正文是否明确是相对上一发布版的完整变化；
- 最大的新功能是否足够醒目且描述到实际能力；
- Windows / macOS / Android / Linux 等受影响平台是否遗漏重要变化；
- 安装与更新行为变化是否写清；
- 是否误写了测试结果、Actions 记录或重发过程；
- 下载区是否足够简洁；
- 仓库 Release 文档与 GitHub Release 正文是否一致。
